## Purge 隔离与互斥

复审发现旧 maintenance CLI 会调用完整服务组合，从而把非过期 workspace 的 `queued/running` 分析误标为 `restart_interrupted`。候选把 maintenance 组合收窄为 SQLite、`SqliteWorkspaceStore` 和 `WorkspaceService`，不再执行应用启动恢复。

生产验收同时插入两个虚构 sentinel：

- 已过期 sentinel 包含 workspace、draft、analysis run、analysis event 和 history，各 1 条。
- 非过期 sentinel 包含 1 个 workspace 和 1 个 `queued` analysis run，初始 event 为 0。
- root 先持有 `/run/lock/mandong/maintenance.lock` 3 秒，再启动 `mandong-purge.service`；oneshot 实际等待 3 秒后执行，证明 purge 与 root 发布工具使用同一 lock。
- 执行后，过期 sentinel 的五类 live 数据均为 0，tombstone 为 1。
- 执行后，非过期 run 仍为 `queued`、`retryable=0`、`terminal_reason=NULL`，event 仍为 0。
- 验收结束后把非过期 sentinel 设为过期并通过正式 purge 删除；生产库中 `sentinel-%` workspace 为 0，两个删除 tombstone 均保留。
- 最终 `mandong-purge.service` 为 success，SQLite `integrity_check=ok`。

共享 lock 的生产属性为：父目录 `root:mandong 0750`，regular lock file `root:mandong 0660`；purge unit 以 `ReadOnlyPaths` 防止 service user 替换 lock inode，竞争等待上限为 30 秒。
